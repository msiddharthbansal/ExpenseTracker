# AI Notes

This project is being built with Claude (Anthropic's Claude Code) as a pair-programming tool. This file is updated as each feature lands.

## Process

Before any code was written, we went through a planning pass: Claude asked clarifying questions about ID generation, validation strictness, list-endpoint scope, and tooling, then proposed an architecture (layered `models` → `storage` → `repository` → `services` → `routes`), identified edge cases, and produced a feature-by-feature roadmap. Implementation proceeds one feature at a time; this entry covers **Feature 1: Add an expense**, plus a small bundled addendum: **`GET /categories`**.

The `GET /categories` addendum was the user's idea, not the AI's: they pointed out that a future UI would need to populate a category picker from the server's fixed category list rather than hardcoding it client-side. Claude agreed it was a good idea, recommended the plural `/categories` path (consistent with `/expenses`) over the originally proposed `/category`, and noted it required no storage/repository changes since it's just a static read of the `Category` enum already defined in `models.py` — so it was bundled into the same pass rather than treated as a separate feature.

This entry also covers **Feature 2: view all expenses** (`GET /expenses`), implemented as its own pass on top of Feature 1; **Feature 3: filter expenses by category** (`GET /expenses?category=`), implemented on top of Feature 2; **Feature 4: category-wise and total expense summary** (`GET /expenses/summary`), which introduces the `services.py` layer that was scaffolded-for but deliberately left empty in earlier passes; and **Feature 5: delete an expense** (`DELETE /expenses/{id}`), the fifth and final feature from the original spec.

**Feature 6: search expenses** was requested afterward, beyond the original 5-feature spec — find expenses by `title`, `category`, `min_amount`, `max_amount`, `start_date`, `end_date`, `month`, and `year`, all combinable. Before writing any code for it, a short planning pass clarified three open design questions with the user: whether to extend the existing `GET /expenses` or add a dedicated `/search` route (chose: extend the existing endpoint, since it's the same "list expenses matching criteria" operation Feature 3 already established), how `title` should match (chose: case-insensitive substring), and how `month`/`year` combine with each other and with `start_date`/`end_date` (chose: every provided filter ANDs together; `month`/`year` are independent, so `month=8` alone means "August, any year").

## What was AI-generated vs. hand-written

Everything in these passes (`src/config.py`, `src/models.py`, `src/storage.py`, `src/repository.py`, `src/services.py`, `src/routes/expenses.py`, `src/routes/categories.py`, `src/main.py`, `tests/`, this README, and the dependency/architecture decisions) was generated by Claude, including Feature 6. Nothing was hand-written from scratch independently of it — the human role here was directing scope, approving/rejecting architectural options via explicit questions, and reviewing the diff before it was accepted. The `GET /categories` feature itself, however, was the user's idea (see Process above), not something Claude proposed unprompted.

`repository.get_all()` (Feature 2) is a thin, single-call read: `[Expense(**item) for item in storage.read_all()]`. It deliberately re-validates each stored dict through the `Expense` Pydantic model on the way out, not just on the way in — this guards against a hand-edited or corrupted `expenses.json` producing malformed API responses; a validation error there surfaces as a 500 rather than silently serving bad data. It intentionally does *not* take `storage.LOCK`: reads don't need it, since `storage.write_all`'s atomic `os.replace` guarantees any read sees either a fully-old or fully-new file, never a torn one — taking the lock here would just add contention with no correctness benefit.

**Feature 3 (filter by category)** extends `repository.get_all()` with an optional `category: Category | None = None` parameter rather than adding a second `get_by_category()` method — there's exactly one code path that reads and parses storage, and filtering is one extra `if` over the already-parsed list. The route exposes this as an optional `?category=` query parameter typed as `Category`, so FastAPI/Pydantic validates it against the enum automatically (invalid values get `422` for free, same as the request-body validation on `POST /expenses`) — no separate validation code was needed.

**Feature 4 (category-wise/total summary)** introduces `src/services.py::compute_summary(expenses: list[Expense]) -> ExpenseSummary` — a pure function with no I/O, no FastAPI dependency, and no `storage`/`repository` coupling, exactly as the original architecture plan called for. The route (`GET /expenses/summary`) fetches data via the same `repo.get_all()` used by Feature 2/3 (one call), then passes the result straight into `compute_summary` — no new repository method needed, since summing/grouping is business logic, not a persistence concern. A new `ExpenseSummary` Pydantic model (`total: float`, `by_category: dict[Category, float]`) was added to `models.py` alongside the existing schemas rather than a separate `schemas.py`, keeping with this project's established pattern of one models file for both domain and API-facing shapes. `compute_summary` accumulates raw (unrounded) floats per category and only rounds once at the very end (`round(x, 2)`), rather than rounding after every addition — rounding incrementally would compound binary-float error across many small transactions; rounding once at the end avoids that.

**Feature 5 (delete)** adds `repository.delete(expense_id: str) -> bool`, following the same lock-guarded read-modify-write shape as `add()`: it filters out the matching expense and only calls `storage.write_all()` if something was actually removed (comparing list lengths before/after) — skipping the write (and the atomic-replace it triggers) when the id isn't found, rather than always writing an unchanged file. The route types the path parameter as `expense_id: uuid.UUID` rather than `str`, so FastAPI/Pydantic rejects a malformed id with `422` automatically before the request ever reaches the repository; a well-formed but non-existent id reaches `repository.delete()`, gets a `False` back, and the route turns that into `404`. This matches the edge-case decision made in the original planning pass: malformed input shape → `422`, well-formed-but-not-found → `404`. Success returns `204 No Content` with no body, per REST convention for `DELETE`.

**Feature 6 (search)** extends `repository.get_all()` from its single `category` parameter (Feature 3) to eight independent optional keyword arguments — `category`, `title`, `min_amount`, `max_amount`, `start_date`, `end_date`, `month`, `year` — each applied as its own `if <param> is not None:` narrowing pass over the already-parsed list, exactly matching the style the `category` filter already established. This keeps `repository.get_all()` a plain, trusting function: it does not itself validate that `min_amount <= max_amount` or `start_date <= end_date`, because that validation already happened one layer up, before `repository` was ever called (see next paragraph) — consistent with this project's existing convention of validating at the API boundary (`ExpenseCreate`) and trusting internal code below it.

The query-param side introduces a new `ExpenseFilter` Pydantic model in `models.py` (all 8 fields optional, with a `model_validator` rejecting `min_amount > max_amount` or `start_date > end_date`) and a route signature change from `category: Category | None = None` to `filters: Annotated[ExpenseFilter, Query()]`. This uses FastAPI's "Query Parameter Models" feature (`Annotated[SomeModel, Query()]`), which flattens a Pydantic model's fields into individual top-level query parameters automatically — `GET /expenses?category=Food&title=coffee&max_amount=10` works exactly as if each were declared as a separate function parameter, and the model's `model_validator` still runs, producing a proper `422` on an invalid range. Because this was a load-bearing assumption for the whole design (get it wrong and the route wouldn't parse query params correctly at all), it was verified empirically *during planning*, before committing to the approach: a throwaway script built a minimal FastAPI app with the same `Annotated[Model, Query()]` pattern against the actual pinned `fastapi==0.115.6`, called it with `TestClient`, and confirmed both the flattening and the `422`-on-invalid-range behavior actually happen — not assumed from documentation.

## What was validated, tested, or changed, and why

- **Actually ran the code, not just read it.** After Claude wrote the add-expense endpoint, it was smoke-tested manually (success case, negative amount, invalid category, blank title) before the formal test suite was written, to catch integration issues early.
- **Verified a floating-point assumption instead of trusting it.** A test asserts `round(1.005, 2) == 1.0`. Rather than assume standard rounding, Claude ran `python3 -c "print(round(1.005, 2))"` directly and confirmed the actual output (`1.0`, due to binary float representation) before writing the assertion — this is the kind of thing that's easy to get wrong by "just knowing how rounding works."
- **Full automated test suite run and passing** (33 tests: 11 repository unit tests, 3 services unit tests, 19 route integration tests via `TestClient`) covering the success path and edge cases (negative/zero amount, blank title, invalid category, invalid date, missing field, `GET /categories` returning the full enum list, `GET /expenses` with and without data, `GET /expenses?category=` filtering, `GET /expenses/summary` — empty state, multi-category breakdown, explicit floating-point-drift rounding via `0.1 + 0.2` — and `DELETE /expenses/{id}` — success, non-existent id, deleting the same id twice, and a malformed id).
- **Verified the summary's dict-with-enum-keys serialization actually works, not just assumed it.** `ExpenseSummary.by_category` is typed `dict[Category, float]`; before trusting it, the test suite was run and the JSON response was inspected to confirm Pydantic v2 serializes `Category` enum dict keys as their plain string values (`"Food"`, not `"Category.FOOD"`) — the same class of enum-serialization mistake already caught once before in `repository.add`'s logging (see below).
- **README commands verified on a simulated clean checkout**, not just assumed to work: the tracked project files were copied to an isolated temp directory (excluding `.venv`, `.git`, `data/`, caches) and the exact `pip install`, `pytest`, and `uvicorn` commands from the README were executed there from scratch, including a live HTTP request against the running server and confirming the JSON file was written correctly.
- **Caught and fixed a logging bug during review**: the first version of `repository.add` logged the raw enum (`Category.FOOD`) instead of its string value (`Food`); changed to `expense.category.value` after noticing it in the smoke-test output.
- **Verified FastAPI's Query Parameter Models feature actually works, before designing around it** (Feature 6): rather than trust prior knowledge of a FastAPI feature that might not exist in, or might behave differently in, the exact pinned version (`fastapi==0.115.6`), Claude wrote and ran a standalone diagnostic script against the real installed package during the planning phase — confirming both the query-param flattening and the `422`-on-invalid-range behavior — before the plan was written or any project code touched. This is the same "verify, don't assume" discipline as the earlier `round(1.005, 2)` and enum-dict-key checks, applied one step earlier, at design time instead of after the code was written.
- **Regression-checked backward compatibility after changing `repository.get_all()`'s signature.** Feature 6 changes `get_all()` from one parameter to eight; before adding any new tests, the full existing 33-test suite was re-run to confirm all prior call sites (`repository.get_all()`, `repository.get_all(category=Category.FOOD)`, and the `?category=Food` route tests) still passed unmodified — verifying the new optional parameters are additive, not breaking, rather than assuming it from reading the diff.
- **Full automated test suite run and passing after Feature 6** (49 tests total: 18 repository unit tests, 3 services unit tests, 28 route integration tests via `TestClient`), covering every filter dimension individually, combined filters (AND semantics), no-match cases, and both invalid-range and invalid-month `422` cases.

## AI suggestions considered and not used

- **Auto-increment integer IDs** — considered as an alternative to UUID4, but rejected: it requires reading the whole file to compute the next ID and is more prone to reuse bugs after deletes. UUID4 was chosen instead.
- **Async file I/O (`asyncio.Lock` + `run_in_executor`)** — considered for the storage layer, but rejected as unnecessary complexity for a small local-JSON-file API. Sync `def` route handlers (which FastAPI runs in a threadpool automatically) plus a plain `threading.Lock` around the read-modify-write section is simpler and sufficient at this scale.
- **Free-text, normalized category strings** — considered, but a fixed `Category` enum was chosen instead, to prevent near-duplicate categories (e.g. "Food" vs "food" vs "Foods") from polluting the category-wise summary that a later feature will build.
- **Building out `repository.get_all()` / `repository.delete()` / `services.py` now, ahead of need** — rejected. Only `repository.add()` exists so far because it's the only operation Feature 1 calls; premature stubs for unimplemented features were deliberately left out.
- **Pagination / sorting / date-range query params on the list endpoint** — considered as a "nice to have" beyond the spec, but rejected to keep the API surface matching exactly what was asked for.
- **Taking `storage.LOCK` inside `repository.get_all()`** — considered for symmetry with `add()`, but rejected: a plain read doesn't need it given the atomic-write guarantee already in `storage.write_all` (see above), and adding it would only add unnecessary contention between concurrent reads and writes.
- **A separate `GET /expenses/by-category/{category}` route or a `repository.get_by_category()` method** — considered for Feature 3, but rejected in favor of an optional query parameter on the existing `GET /expenses`: it's the same resource and the same underlying read, so a second route or method would just duplicate the read-and-parse logic already in `get_all()` for no functional benefit.
- **Rounding after every accumulation in `compute_summary`** (e.g. `total = round(total + expense.amount, 2)` inside the loop) — considered, but rejected in favor of summing raw floats and rounding once at the end, to avoid compounding binary-float rounding error across many additions.
- **Wrapping `compute_summary` behind its own `Depends()`-injected service object** — considered for consistency with the repository's DI pattern, but rejected: it's a pure, stateless function with no I/O or external dependency to inject, so wrapping it in DI would add indirection without any benefit. The existing `Depends(get_repository)` remains the only injected dependency; `compute_summary` is called directly.
- **A separate `repository.get_summary()` method that reads storage and computes the summary in one step** — considered, but rejected: it would blur the repository/service boundary (persistence vs. computation) that the architecture is built around, and the route already gets the same result in one line by composing the existing `repo.get_all()` with `services.compute_summary()`.
- **Typing the delete path parameter as `str` and validating UUID format manually** — considered, but rejected in favor of typing it `uuid.UUID` directly: FastAPI/Pydantic then does the format validation (and the `422` response) for free, matching the same "let the framework validate, don't hand-roll it" approach used everywhere else in this project (`Category` enum on the request body and query param).
- **Always calling `storage.write_all()` in `repository.delete()`, even when the id isn't found** — considered for symmetry with `add()` (which always writes), but rejected: deleting a non-existent id is a no-op, and writing an unchanged file would trigger a pointless atomic replace on every 404. Comparing list length before/after avoids that.
- **A dedicated `GET /expenses/search` route, separate from `GET /expenses`** — this was Claude's initial framing of the design question, presented to the user as an option. The user chose to extend the existing `GET /expenses` instead: search and "filter by category" are the same underlying operation (list expenses matching some criteria) that Feature 3 already established as query params on one endpoint, so a separate route would have duplicated that pattern for no real benefit.
- **Exact (case-insensitive) title matching instead of substring** — presented as the simpler alternative, but the user chose substring matching: a "search" feature that requires the precise title defeats much of the point of searching.
- **Requiring `month` and `year` to be given together, and treating them as mutually exclusive with `start_date`/`end_date`** — presented as a stricter alternative that would prevent overlapping range specifications, but the user chose the simpler "every provided filter ANDs together" semantics instead, consistent with how every other filter in this endpoint already composes.
- **Passing the `ExpenseFilter` Pydantic object itself into `repository.get_all()`**, instead of unpacking it into individual keyword arguments at the route (`repo.get_all(**filters.model_dump())`) — considered, but rejected to keep `repository.py` decoupled from the API-layer schema: existing direct calls like `repository.get_all(category=Category.FOOD)` in the unit tests continue to work unchanged, and the repository layer doesn't need to know an HTTP-facing Pydantic model exists at all.
